## Explanation for the reviewer

Promisory is a native Forge app with Forge Remote. All three release profiles request `auth.appUserToken.enabled: true` and `read:app-user-token`; none requests an app system token. Hosted product calls use `asUser()`. The remote uses only the current invocation's `x-forge-oauth-user` token and the Atlassian API destination from a verified, installation-bound FIT. It never accepts an API destination or effective identity from a browser or model and never persists OAuth tokens for replay.

Before a remote action, the active OAuth account must match the FIT principal. Before a Jira due-date PUT, an issue-scoped `/rest/api/3/mypermissions` response must grant Browse Projects, Edit Issues, and Schedule Issues. The remote checks these permissions again immediately before dispatch. Errors, missing permission entries, revoked permissions, malformed responses, missing user tokens, or mismatching identities prevent the write. A separate Decionis grant and claim are still required. The final PUT uses the same user token, so native Jira authorization remains enforced at the write itself.

Connection logs retain bounded outcome metadata and a generated request correlation ID, without account identifiers, source content, credentials, or OAuth headers. Independent user intent and the allowlisted Jira date snapshot may reach the executor; Teamwork Graph data and derivatives remain inside Atlassian.

The production dependency scan is clean after the transitive Zod/glob updates. The latest Forge CLI 15.1.0 retains findings in its own shrinkwrapped development dependencies; the full scan is not described as clean. The executor image excludes the CLI. Marketplace production version 4.3.0 and the hardened executor were deployed on 20 November 2026. The installed development check produced matching Forge and remote observations of FIT, signed-envelope, and active-user verification without a Jira write.

See [decision 0023](../decisions/0023-remote-user-permission-verification.md) and the [verification evidence](../evidence/2026-11-20-remote-authorization/README.md). The evidence records the distinction between the previously deployed checks, new hardening, and the version actually resubmitted.

## Input validation explanation (9.1)

Forge resolver and Rovo inputs pass through the shared, versioned Zod contracts before domain actions run. The contracts reject unknown command fields and validate enums, Booleans, integer ranges, unique bounded identifier lists, text lengths, valid calendar dates, ISO timestamps, and IANA time zones. Source IDs are restricted to 1–20 decimal digits; trusted installation, cloud, and principal identity comes from Forge context rather than caller overrides.

SQL uses prepared statements with bound values. The SQL `LIMIT` is interpolated only after integer/range validation. JQL is fixed application syntax with a validated numeric project ID; GraphQL uses fixed queries and separate variables. User text is rendered through React's normal escaping, with no raw HTML insertion or executable user input. These are context-specific injection defenses rather than indiscriminate removal of characters from user text.

The remote HTTP server accepts three fixed POST routes and limits request bodies to 16,000 bytes. Remote payloads and provenance are validated against narrow contracts. The supported write body contains only the validated Jira due date. The API destination must be the verified FIT's `https://api.atlassian.com/ex/jira/<bound-cloud-id>` origin and exact installation path, without user info, query, or fragment; product calls refuse redirects. There is no UI/model-supplied arbitrary URL, recipient, payload, or effective-identity override. Operator configuration separately requires an HTTPS authority URL. Untrusted input never selects a weaker policy or bypasses the execution grant.
